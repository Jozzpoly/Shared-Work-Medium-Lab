## Why this exists

Medium currently has several different kinds of "current":

1. **accepted public baseline** — what `main` has actually accepted;
2. **active draft frontier** — work living in open PRs/branches that may be newer but is not accepted baseline;
3. **live/private research** — conversation/Library work that may be newer still and is not automatically public or repo authority.

Those must not be collapsed into one truth plane.

At the time this specimen was created:

- public accepted baseline: `main@d190d17db8edb5e6e41f8e5777fe2dc0894280d1`;
- `docs/RESEARCH_STATE.md` says its last material update is 2026-10-04;
- draft PR #8 contains the newer source-bound capability-expedition evidence;
- draft PRs #5/#6 contain Quiet Presence / exchange-window evidence;
- draft PR #4 contains the MP-1 controlled apparatus;
- newer live research may exist outside the public repository and must not be invented or treated as public authority.

The purpose of this branch is only to test whether **explicit topology** makes recovery safer than telling a fresh agent that one large document is simply "the current live state".

## Evaluation question

For a fresh agent with a real task:

> Does this explicit topology help it reach the right authority faster, while preserving the distinction between accepted baseline, draft evidence and volatile live state?

A useful outcome may be:

- use accepted baseline;
- inspect one draft PR;
- inspect live source;
- decide nothing newer is relevant;
- or correctly report that the public repo is insufficient for the requested live claim.

The goal is not maximal retrieval.

## Falsifiers

Reject or revise this pattern if:

- fresh agents still treat draft work as accepted truth;
- the extra routing layer increases reading burden without changing decisions;
- it becomes another stale handoff that must be manually maintained everywhere;
- project-local entrypoints alone already solve the problem;
- the topology pressures all projects into the same representation.

# North Star

## Core purpose

Build a developing medium for shared work that simultaneously:

1. **increases joint capability** — better perception, action, continuity, orientation, and practical reach for agents;
2. **reduces Owner orchestration cost** — less manual context transfer, recovery, routing, and technical administration;
3. supports **shared reality, different minds** — Browser, Codex, Work, future models, tools, and humans may hold different interpretations while referring to the same project reality;
4. preserves **Owner judgement, freedom, and serendipity** instead of optimizing everything around one roadmap;
5. enables **emergent affordances** — useful workflows should be discoverable from the environment, not only pre-programmed.

## Founding insight

The project began after a browser experiment where a model was given a live website and a broad goal, but no explicit procedure. Semantic page structure, stable URLs, and reasoning were enough for the model to discover a batch workflow that had not been designed in advance.

Working hypothesis:

> A sufficiently legible and actionable environment can multiply effective agent capability without changing the model.

## The system is a prosthesis, not only memory

The environment may eventually provide agent-native equivalents of:

- **eyes** — semantic views, repository state, artifacts, change views;
- **ears** — events and changes outside the active conversation;
- **hands** — MCP actions, Codex, Work, browser/computer-use, repository actions;
- **external memory** — durable project history and sources;
- **proprioception** — awareness of available capabilities, active runs, and confirmed operational state;
- **joint attention** — stable reference to the same object, code region, timestamp, capture, or UI state;
- **peripheral vision** — the ability to notice anomalies and promising side paths without turning them into mandatory roadmap tasks.

The goal is not to imitate human UI when a more semantic agent-native sense or actuator is better.

## Owner invariants

The Owner must not become the glue of the system.

The environment should reduce the need to manually:
- restate context across chats;
- explain Browser context to Codex;
- remember which artifact or document is current;
- recover work after an interrupted session;
- route every task between tools;
- understand low-level infrastructure choices in order to keep the collaboration coherent.

At the same time, the system must preserve the Owner's unique domain:
- vision;
- experiential judgement and feel;
- intuition;
- direction;
- the right to reject a mechanically green result;
- the right to change direction abruptly;
- the right to explore a strange side path because it might matter.

## Anti-drift tests

Before a material design decision, ask:

- Does this increase real joint capability?
- Does it reduce, or at least not increase, Owner burden?
- Is it solving observed collaboration friction rather than an elegant infrastructure problem?
- Does it preserve rich sources and provenance?
- Does it keep freedom and serendipity alive?
- Does it avoid unnecessary dependence on one model, UI, vendor, or workflow?
- Could a smaller experiment reveal more before we build infrastructure?

If the answers deteriorate, implementation should pause and recover the intent.

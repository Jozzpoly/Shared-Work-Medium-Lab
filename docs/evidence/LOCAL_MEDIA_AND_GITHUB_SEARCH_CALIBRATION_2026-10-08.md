# Local media convergence + GitHub search calibration — 2026-10-08

**Status:** source-bound reconnaissance · sensor calibration · not architecture.

## Purpose

Two questions were tested together because they are easy to conflate:

1. Are multiple projects independently developing local recovery/evidence/authority media?
2. Can the current Browser GitHub search body discover those local media reliably from problem-language alone?

The first question is about the ecosystem.
The second is about one current sensor.

A failure of the search body is **not** evidence that the ecosystem lacks the relevant knowledge.

## Convergence judgement

The projects do **not** converge on one file shape, one schema or one workflow.

They do repeatedly defend relations such as:

- current != historical;
- accepted != candidate;
- machine PASS != Owner/product PASS;
- donor != target authority;
- result != next action;
- plan != authorization;
- presentation != source truth;
- local scientific instrument != global project state.

This supports only a bounded hypothesis:

> cross-project infrastructure may gain more by preserving local authority boundaries and making local media reachable than by normalizing all projects into one common state model.

It does not yet establish that Shared Work Medium adds value beyond ordinary tools and good project front doors.

## B. GitHub search sensor calibration

The current Browser GitHub search path was tested with both structural phrases and exact-token controls.

### Broad problem-language probes

Examples:
- `exact fork same future trajectory private state process state`
- `view presentation must not become world authority`
- `Owner feedback outranks machine PASS product evidence`
- `donor evidence not architecture authority`
- `transport disconnect same world actor continuity`

These returned zero useful cross-project hits.

Shorter lexical probes either returned zero results or unrelated repositories.

That alone would not prove weak semantic discovery because query semantics/indexing could be the cause.

### Targeted exact-token controls

The search sensor was then scoped to repositories whose files had already been direct-read successfully.

## Sensor judgement

**FAIL as an ecosystem-coverage sensor in the current Browser body.**

The current search path cannot be treated as evidence that:
- a donor does not exist;
- a project lacks a concept;
- lexical search is sufficient for candidate generation;
- semantic analogy has failed.

It also cannot serve as a fair C0 candidate-generation baseline without separate requalification.

This is a **body/sensor limitation**, not an ecosystem absence claim.

## Consequence for the Peripheral Candidate Generation Probe

A fair ordinary-environment baseline should distinguish:

1. **known-world direct inspection**
   - repository metadata;
   - front door;
   - branch / PR / exact file reads;

2. **activity sensors**
   - repository `pushed_at`;
   - open PRs;
   - recent commits;
   - Opera open tabs/history;
   - other source-native signals;

3. **cold search/discovery**
   - currently unqualified in this Browser GitHub path.

Do not silently use cold code search as a complete ecosystem sensor.

The open research question remains:

> can a relevant unknown local medium enter the receiver's candidate set without Owner routing, while durable truth and interpretation remain local?

No PASS is claimed here.

## Anti-architecture note

This finding does **not** justify:
- a central capability registry;
- a global CURRENT schema;
- mirroring every project event into Slack;
- continuous scanning of every repository;
- a universal project-medium protocol.

The next useful evidence should compare sparse peripheral sensing against real existing environmental traces, with source verification after candidate entry.

## Owner-wide GitHub activity sensing — bounded negative

A follow-up tested whether the existing GitHub connector could act as a cheap source-native project-activity peripheral instead of copying events into Slack.

Results:
- no GitHub Notifications/Events inbox tool is exposed in the current connector namespace;
- `list_repositories` returns accessible repositories but strips `pushed_at` / `updated_at`, so it cannot rank current project heat;
- global `search_issues` without a repository scope searches broad GitHub, not the user's installation-visible repository set;
- `user:Jozzpoly updated:>=2026-10-07` and `author:Jozzpoly updated:>=2026-10-07` returned zero despite independently verified fresh PR activity, so those query forms are not qualified as owner-wide activity sensors here;
- direct `GET /users/Jozzpoly/events/public` through the generic GitHub fetch tool is rejected as an unsupported endpoint.

Bounded conclusion:

> **The current GitHub connector does not expose a trustworthy one-call owner-wide activity stream.**

This does not imply GitHub lacks such APIs generally. It is a claim about the current Browser connector body.

Practical consequence:
- use repo-local source-native front doors once a candidate repo is known;
- use Opera/open-tab/history traces and other working-set evidence for candidate generation;
- do not interpret empty global GitHub search results as project silence;
- do not create a copied Slack feed merely to compensate for this absence.

This strengthens the existing distinction between **candidate generation** and **source-native verification**.
